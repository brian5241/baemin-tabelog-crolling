# 설계 문서

## 1. 전체 흐름

1. 대상 지역의 타베로그 가게 데이터를 앱 DB에 저장 (자동 크롤링이 아니라 사용자가 직접 연 페이지를 저장하는 방식, 1-1 참고). 평점 원본값을 그대로 저장하고 필터링은 질문 단계에서 동적으로 처리
2. Akinator처럼 스무고개를 하되, 방향은 반대: 사용자가 "이건 별로야"를 골라 소거
3. 결과는 하나가 아니라 여러 개의 후보군으로 남을 수 있음
4. 질문 순서는 고정, 비교적 정확하게 구조화 가능한 항목(가격대·거리·인원 등)을 먼저 물어 후보를 추린 뒤, 리뷰 기반 추상 항목(분위기·사진 등)으로 세부 조정

## 1-1. 데이터 수집 방식과 이용 범위

### 방향: 개인용 + 방안 A (사용자 선호, 최종 확정 대기)

- 처음에는 공개 서비스를 목표로 했으나, 아래 확인 결과에 따라 "문제가 생기면 개인용으로 전환" 원칙대로 **나 혼자 쓰는 개인용 앱**으로 방향 전환
- 데이터는 무조건 타베로그 기준 (다른 서비스 API로 대체하지 않음)
- 앱이 스스로 타베로그에 접속하는 자동 크롤링은 하지 않음. 봇 확인 우회(헤드리스 브라우저 위장, 챌린지 자동 통과, 타베로그 앱 통신 분석 등)도 하지 않음

### 방안 A: 저장 DB + 열람 시 최신화

| 단계 | 타베로그를 여나 | 내용 |
|---|---|---|
| 초기 저장 | 연다 (사람이 직접) | 앱 안 브라우저로 대상 지역 랭킹 목록을 직접 넘기며 페이지마다 "이 페이지 저장". 한 페이지에 약 20곳의 이름·장르·평점·예산·역 거리 저장 |
| 앱 사용 | 안 연다 | 저장된 DB만으로 질문·소거·후보 수 표시·정렬·지도가 앱 안에서 동작 |
| 열람 시 최신화 | 연다 (사용자가 누른 가게만) | 결과에서 가게를 누르면 앱 안 브라우저로 타베로그 가게 페이지가 열리고, 화면에 보이는 그 페이지에서 현재 평점·폐업 여부·상세 정보(개별실, 카운터석 등)를 읽어 DB 갱신 |

- 지켜야 할 선: 화면에 보이지 않게 페이지를 열거나, 사용자가 누르지 않은 가게·다음 페이지를 연달아 자동으로 여는 기능은 넣지 않음 (자동 크롤러가 됨)
- 상세 정보는 처음엔 비어 있고 열어볼 때마다 채워짐. 결측값 정책(정보 없음은 소거하지 않음) 덕분에 비어 있어도 정상 동작
- 새 가게는 찾아오지 못함. 새 지역 추가나 대량 갱신은 목록 페이지를 다시 직접 넘겨 저장

### 최신성 처리 (스냅샷 한계 보완)

- 저장 시점 스냅샷이라 폐업·평점 변화가 즉시 반영되지 않음. 대신 **가게를 고르는 순간에는 항상 최신**이 되도록 설계
- 결과 카드에 수집일 표시, 일정 기간(초안 3개월) 지난 정보는 "오래된 정보"로 표시
- 열람 시 閉店(폐점)·休業(휴업) 표시가 있으면 후보에서 자동 제외, 평점이 사용자 조건 아래로 떨어졌으면 "조건 미달" 표시
- 목록 재저장 시 이전에 있던 가게가 안 보이면 "폐업 또는 순위 하락 가능성"으로 표시

### 기술 조건: 네이티브 앱

- 다른 사이트(타베로그) 화면의 내용을 읽는 건 웹사이트 형태로는 브라우저 보안 규칙상 불가능 → 앱 안에 브라우저 화면을 넣고 그 내용을 읽을 수 있는 **네이티브 앱**으로 제작
- 앱스토어 등록 없이 내 폰에만 설치

### 참고: 방안 B (채택 안 함)

- 질문 답을 타베로그 검색 조건 URL로 바꿔 타베로그 검색 결과를 바로 여는 방식. 평점·폐업 여부가 완전 실시간이고 수집이 필요 없음
- 대신 후보 수 표시, 자체 정렬·지도, 혼밥 판정 등 타베로그 검색에 없는 기능을 포기해야 해서 방안 A 선호
- 방안 C(타베로그 운영사 カカクコム(가카쿠닷컴)에 데이터 이용 허락 요청)는 개인 프로젝트에 허락 가능성이 낮아 보류

### 배포 시 위험 (2026-10-02 정리)

약관 9(1)[1]·8(3)은 영리 여부와 무관하게 "복제·배포"를 문제 삼으므로, 크롤링을 안 해도 배포 방식에 따라 걸릴 수 있음.

| 배포 방식 | 위험도 | 이유 |
|---|---|---|
| 나 혼자 사용 | 낮음 | 비영리 개인 이용. 9(1)[1]의 "법령상 인정되는 경우" 예외(일본 저작권법 30조 사적 복제)에 가까움 |
| 빈 앱을 지인과 공유, 각자 직접 저장 | 회색지대 | 데이터를 나눠주진 않지만 "데이터 추출 도구"로 볼 여지 (9(1)[7] 운영 방해, [12] 부적절 판단) |
| 내가 모은 DB를 담아 배포 | 높음 | 타베로그 정보 복제·배포. 9(1)[1]·8(3)에 정면 해당 |
| 광고·유료 기능 추가 | 높음 | 위에 더해 6(1)[1] 영리 금지, 리뷰 이용 시 1건당 1만 엔 청구 조항 |

- 앱스토어도 애플 심사 가이드라인 5.2.2(다른 서비스 콘텐츠 사용 시 해당 서비스 약관상 허용 필요) 등으로 등록 거절 가능성이 높음
- 리뷰 원문은 저작물이라 DB에 통째로 저장하지 않음. 가게 기본 정보(영업시간, 가격대, 장르 등 사실 정보) 위주로 저장
- 법률 판단은 확정된 것이 아님. 공개 배포를 검토하게 되면 타베로그 문의 또는 전문가 확인 필요

### 타베로그 확인 결과 (2026-09-25)
  - **robots.txt**: 일반 크롤러(`User-agent: *`) 기준으로 가게 페이지·목록 페이지는 금지 경로가 아님. 다만 Bing·Baidu 등 검색엔진 크롤러에도 Crawl-delay 5~10초를 요구하고, GPTBot·Google-Extended(AI 학습용)는 전면 금지
  - **이용약관**: 크롤링 자체를 명시적으로 금지하는 조항은 없으나 다음 조항에 걸림
    - 9(1)[1] (금지 행위): 사전 동의 없이 타베로그 정보를 복제·배포·전매하거나 그 목적으로 보관하는 행위 금지 → 수집해서 DB에 저장하고 보여주는 구조 자체가 해당
    - 8(3) (저작권): 콘텐츠의 복제·편집·게재·공중송신 금지
    - 6(1)[1] (전용 금지): 영리 목적의 이용·접근 금지 → 개인·비영리 이용은 해당 없음
    - 6(1)[2]·[3] (리뷰): 리뷰 무단 전재·이용 금지. 영리 목적 이용 시 리뷰 1건당 1만 엔 청구 가능
  - **기술적 차단**: 가게 목록 페이지(rstLst)는 첫 요청부터 HTTP 403 + `Cf-Mitigated: challenge` (Cloudflare 봇 확인 요구). 요청 간격과 무관하게 차단됨. 장르 목록 페이지(cat_lst), robots.txt, 약관 페이지는 정상 응답
  - **결론**: 공개 서비스로 타베로그 데이터를 저장·표시하는 건 사전 동의 없이 불가. 자동 수집은 봇 확인을 우회해야만 가능하며, 우회는 하지 않는다. 요청 간격(예: 0.5초)을 두는 건 서버 부담을 줄이는 예의일 뿐 차단 해결책이 아님 (첫 요청부터 차단되고, 검색엔진에도 5~10초를 요구)
  - 일본은 크롤링에 엄격한 편 (2010년 오카자키 시립도서관 사건: 초당 1회 수준 크롤링으로 업무방해 혐의 체포, 이후 기소유예)
- 공식 API(ホットペッパーグルメ(핫페퍼 그루메), Google Places)로 대체하는 안은 "타베로그 기준이어야 의미가 있다"는 이유로 채택하지 않음

## 2. 구조화(concrete) vs 추상(abstract) 데이터

- **구조화**: 타베로그 필드에서 바로 뽑히는 값 (가격대, 예약 필수, 주차, 음주 가능, 장르 등). 단 일부는 누락/오기재가 잦아 리뷰로 보정 필요 (주차, 음주 가능 등)
- **추상**: 리뷰 텍스트에서 추론해야 하는 값 (분위기, 가성비 vs 맛, 인테리어, 포토제닉 여부 등). 정확도가 낮으므로 후보군이 어느 정도 추려진 뒤 적용

### 데이터 모델 방향

- `restaurants` 테이블: 구조화 필드만 (가격대, 대분류, 주차, 예약필수, 미슐랭 여부 등). 목록 페이지 저장 시 기본 필드를 채우고, 상세 필드는 가게 페이지 열람 시 채움. `collected_at`(수집일), `detail_collected_at`(상세 수집일), `status`(영업/휴업/폐점) 컬럼 포함
- `restaurant_tags` 테이블: `{restaurant_id, tag, confidence, source}` — 리뷰 기반 추론값. `source`로 구조화/추론 출처 구분, `confidence`로 신뢰도 임계값 튜닝 가능하게
- 미슐랭 여부는 타베로그 자체 데이터가 아니라 별도 소스(미슐랭 가이드)와 매칭 필요
- 프랜차이즈 여부도 타베로그에 명시적 필드가 없을 가능성이 높아 브랜드명 매칭/휴리스틱 필요할 수 있음
- 흡연 필드는 boolean이 아니라 **금연 / 분연 / 흡연가능 / 가열식전용** enum으로 설계 (일본은 2020년 개정 건강증진법 이후에도 기존 소규모 매장 경과조치, 흡연전용실 등 예외가 다수 존재)

### 결측값 정책 (확정)

- 필드 값이 없는 가게는 **소거하지 않고 후보에 남긴다**. 결과 카드에는 해당 항목을 "정보 없음"으로 표시
- 최종 정렬에서는 조건 충족이 확인된 가게를 우선하고, 정보 없음인 가게는 그 뒤에 배치
- `priority_flag` 문항(Q13·14)에서는 태그가 없으면 중립 점수로 처리 (가점·감점 모두 없음)

### 기준 위치 · 거리 계산 (확정)

- 기준 위치는 **역 선택이 기본**, 현재 위치(기기 GPS)는 보조 옵션. 여행 계획 용도라 사용자가 현지에 없는 경우가 많고, 권한·오차·개인정보 문제가 없음
- 역 좌표는 공개 데이터셋(駅データ.jp 등)을 DB에 적재. 같은 역의 노선·운영사별 레코드는 역 그룹 코드로 묶어서 자동완성에 하나로 표시하고, 대표 좌표 하나를 사용. 대표 좌표는 그룹 내 노선별 좌표의 평균(중심점)으로 계산 (특정 노선 쪽으로 치우치지 않도록)
- 이름이 비슷해도 실제로 다른 역(西武新宿, 新宿三丁目, 新宿西口 등)은 별도 항목으로 표시
- 가게 좌표는 타베로그 페이지 저장 시 함께 수집 (목록·가게 페이지 중 어디에 있는지 확인 필요)
- 거리는 haversine 직선거리 × 보정계수(초안 1.3)로 계산, 도보 1분 = 80m로 환산. 외부 API 없음
- 지도 표시는 Leaflet + OpenStreetMap. 실제 도보 경로가 필요해지면 OpenRouteService 검토

### 후보 수 표시 (확정)

- 매 질문 화면에 현재 남은 후보 수를 표시 (예: "남은 후보: 42개")
- 선택지마다 **그 선택지를 고르면 남는 후보 수**를 함께 표시 (예: "한식 (3) / 일식 (38) / 양식 (12)")
  - `multi_select`(소거형)는 이미 고른 항목을 반영해서, 해당 항목을 추가로 뺐을 때 남는 수를 표시하고 선택할 때마다 갱신
  - `threshold`, `binary`, `single_select`도 같은 규칙. `setup` 질문 중 필터 역할을 하는 Q5(방문 시간대)도 표시
  - `priority_flag`(Q13·14)는 후보를 줄이지 않으므로 표시하지 않음
  - "정보 없음" 가게는 소거되지 않으므로 개수에 포함
- 남는 후보가 0개인 선택지는 비활성화. 이 규칙으로 질문 도중 후보가 0개가 되는 상황 자체를 막음

### 결과 정렬 · 표시 (확정)

- 남은 후보는 개수 제한 없이 **전부 표시**
- 정렬 우선순위
  1. 조건 확인 여부: 사용자가 조건을 건 항목이 모두 확인된 가게가 먼저, "정보 없음"이 섞인 가게는 뒤로 ("상관없음"을 고른 항목은 무관)
  2. Q13·14 점수: 해당 문항에서 "후순위로 보낼 곳"을 골랐을 때만 적용 (v1에서는 두 문항 보류로 미적용)
  3. 타베로그 평점 내림차순
  4. 리뷰 수 내림차순 (동점 처리)

## 3. 질문 타입 분류

| 타입 | 설명 |
|---|---|
| `setup` | 소거가 아니라 조건을 설정하는 질문. 선택형 문구 허용 (Q0 기준 위치, Q1 찾는 곳, Q5 방문 시간대) |
| `single_select` | "빼고 싶은 것" 중 하나를 고름 (상관없음 = 필터 off) |
| `multi_select` | "빼고 싶은 것"을 여러 개 고름. 아무것도 고르지 않으면 상관없음 |
| `binary` | 빼고 싶은 조건 하나에 대해 "해당 조건 / 상관없음" 중 고름 |
| `threshold` | 순서형(ordinal) 값에 상한 또는 하한 임계값 설정, 단조 필터. 선택지는 "N 이상 / N 미만"으로 짧게 표기 ("N까지" 같은 선택형 문구 금지) |
| `priority_flag` | 후보를 소거하지 않고 "후순위로 보낼 것"을 고름. 리뷰 기반 점수로 남은 후보를 재정렬 |

**질문 문구 원칙**: 소거 질문은 "빼고 싶은 ~", 정렬 질문은 "후순위로 보낼 ~"으로 묻는다. 선택형 문구("~를 원하나요?")는 `setup` 질문에만 쓴다.

### Q13·14 v1 보류 (확정)

- 분위기·사진은 추상 항목이라 판정 근거가 필요한데, 현재 데이터 수집 가능 여부와 분위기 태그 존재 여부가 모두 미확인이라 v1에서는 질문을 비활성화
- 두 문항은 소거 없이 정렬만 하므로 빠져도 소거 로직에 영향 없음. 태그 테이블(`restaurant_tags`)과 정렬 규칙 자리는 유지해서 나중에 질문만 켜면 되도록 함
- 분위기 중 구체적인 부분은 다른 질문이 담당: 캐주얼한 가게 형태는 Q12, 개별실·좌식 방 등 좌석 형태는 Q7 판정 근거
- 재활성화 조건: 데이터 수집 방식 확정 + 분위기 신호 확인. 후보 신호는 타베로그 가게 정보의 空間・設備(공간·설비: おしゃれな空間, 落ち着いた空間 등), ロケーション(입지: 夜景が見える, 隠れ家レストラン 등), 利用シーン(이용 장면: デート, 接待 등). 가게·사용자 입력 정보라 과장·결측이 있을 수 있어 가점용으로만 사용하고, 리뷰 분석은 보완용

### Q6 가격대 구간 (확정)

| 대상 | 선택지 |
|---|---|
| 음식점 런치 | 1000엔 이상 / 2000엔 이상 / 3000엔 이상 / 상관없음 |
| 음식점 디너, 술집 | 3000엔 이상 / 5000엔 이상 / 10000엔 이상 / 20000엔 이상 / 상관없음 |
| 카페·디저트, 빵·과자 | 1000엔 이상 / 2000엔 이상 / 상관없음 |

- 일본 음식점 예산은 런치 1000~2000엔대, 디너 3000~10000엔대에 몰려 있어 시간대·카테고리별로 구간을 분리
- 구간 경계는 타베로그 예산 구간 경계에 맞춤. 가게 예산 구간의 시작값이 선택 금액 이상이면 소거 (예: "3000엔 이상" 선택 → ¥2,000～¥2,999 유지, ¥3,000～¥3,999 소거). 더 싼 가게는 항상 남음
- 예산은 리뷰어 실사용 금액 집계를 우선, 없으면 가게 입력 예산, 둘 다 없으면 "정보 없음"으로 유지. 필드 구조는 페이지 직접 확인 시 점검

### Q7 일행 조건 (확정)

| 선택지 | 소거 대상 | 판정 근거 |
|---|---|---|
| 혼자 가기 불편한 곳 | 카운터석이 없거나 2인 이상만 받는 가게 | 카운터석 정보, 예약 조건, 혼밥 관련 리뷰 태그 |
| 단체(5명 이상) 불가한 곳 | 단체석·座敷(자시키, 좌식 방)·個室(개별실)·貸切(대관) 정보가 모두 없는 가게 | 좌석 형태 정보 |
| 상관없음 | 없음 | |

- 타베로그 좌석 수는 가게 전체 좌석이라 1~2인 판정에 쓸모가 없고, 좌석이 많아도 전부 카운터석이면 단체가 못 앉음. 그래서 인원 수 대신 좌석 형태로 판정
- 2인, 3~4인은 거의 모든 가게가 가능해 선택지에서 제외
- 카운터석·좌석 형태 필드 구조는 페이지 직접 확인 시 점검

### 장르 → 카테고리 매핑 (확정)

- 이자카야 계열(居酒屋, ダイニングバー, 立ち飲み, バル, ビアガーデン·ビアホール)은 음식점과 술집 양쪽에 소속 (확정)
- Q4 화면 표시는 10개 그룹을 제목 아래 묶어서 보여줌 (확정). 소거 로직은 10개 그룹 단위 그대로
  - **일식**: 스시·해산물 / 라멘·면류 / 일식 일반 / 이자카야·야키토리
  - **고기구이·스테이크**: 야키니쿠·스테이크 등
  - **그 외**: 중식 / 한식 / 양식 / 아시아·에스닉·카레 / 기타
  - 라멘은 일본에서 사실상 일식이지만, 가게 수가 많고 식사 성격이 뚜렷해서 일식 안의 독립 그룹으로 둠 (타베로그도 和食과 별도 대분류)
- 가게에 장르가 여러 개 붙은 경우 (확정)
  - Q1(찾는 곳): 장르 중 하나라도 해당하면 그 카테고리에 소속 (복수 소속 허용)
  - Q4(장르 그룹): 주 장르(타베로그 표기상 첫 번째 장르)만 기준. 첫 번째 장르가 실제 주 장르인지는 페이지 직접 확인 시 점검
- 디저트(スイーツ)는 매장 형태에 따라 나눔 (확정)
  - **카페·디저트** (앉아서 먹는 곳): カフェ・喫茶店 대분류 전체(カフェ, 喫茶店, 甘味処, フルーツパーラー, パンケーキ, コーヒースタンド, ティースタンド, ジューススタンド, タピオカ) + かき氷
    - 예: ひみつ堂(빙수), 千疋屋総本店 フルーツパーラー, 竹むら(甘味処), 幸せのパンケーキ
  - **빵·과자** (진열장에서 골라 포장하는 곳): パン・サンドイッチ 대분류 전체 + かき氷를 제외한 スイーツ 대분류 전체(ケーキ, 洋菓子, 和菓子, たい焼き, ドーナツ, チョコレート 등)
    - 예: とらや, BAKE CHEESE TART, 浪花家総本店
  - 케이크와 카페 장르가 함께 붙은 가게(예: HARBS)는 Q1 복수 소속 규칙에 따라 양쪽에 모두 노출
  - 타베로그도 甘味処·フルーツパーラー·パンケーキ를 カフェ・喫茶店 아래에 두므로 같은 기준
- 고기 그룹은 "고기가 들어간 음식"이 아니라 "고기 자체가 주인공인 가게"로 한정하고 이름을 **고기구이·스테이크**로 변경 (확정)
  - 고기가 들어간 음식으로 정의하면 돈카츠·규동·라멘·햄버그 등 거의 모든 그룹을 침범하고, "고기 빼줘"를 고르면 남는 가게가 거의 없어짐
  - 소속: 焼肉, ホルモン, ジンギスカン, ステーキ, 鉄板焼き, 肉料理 전체(牛料理, 豚料理, 馬肉料理, ジビエ料理), バーベキュー, シュラスコ
  - 원래 요리 계열로 배치: とんかつ·牛カツ·すき焼き·しゃぶしゃぶ·牛タン·牛丼·かつ丼·豚丼·もつ鍋 → 일식 일반, ハンバーグ·ハンバーガー → 양식
  - "고기가 전혀 없는 곳"은 장르 소거와 다른 요구이므로, 필요하면 채식 옵션 여부를 별도 질문으로 검토
- 스시·해산물 그룹 범위 (확정). 고기구이·스테이크와 같은 "재료 자체가 주인공인 가게" 원칙
  - 소속: 寿司 전체(寿司, 回転寿司, 立ち食い寿司, いなり寿司, 棒寿司), 海鮮(海鮮, ふぐ, かに, あんこう, かき), うなぎ·あなご·どじょう, 海鮮丼, シーフード, オイスターバー
  - すっぽん은 해산물보다 고급 일식 코스에 가까워 일식 일반으로 이동
  - 天ぷら는 요리법 기준 장르라 일식 일반, ろばた焼き는 술과 먹는 형태라 이자카야·야키토리 유지
  - 回転寿司와 고급 스시집의 차이는 Q3(프랜차이즈), Q6(가격대)에서 걸러지므로 그룹을 나누지 않음
- 그 외 겹치는 장르 배치 (확정). 원칙: **애매하면 타베로그 대분류를 따른다** (예외: 火鍋, 鳥料理)

  - 라멘·면류: 担々麺(탄탄멘), 汁なし担々麺(국물 없는 탄탄멘), 刀削麺(도삭면), 台湾まぜそば(타이완 마제소바, 나고야식 매운 비빔면), ちゃんぽん(나가사키 짬뽕), カレーうどん(카레 우동)
    - 刀削麺은 중식 이미지가 강하지만, 사용자가 면류 안에서 알아서 판단할 수 있다고 보고 타베로그 분류를 따름

  - 이자카야·야키토리: 串揚げ(꼬치 튀김), もつ焼き(내장 꼬치구이), 肉バル(고기 중심 캐주얼 바), ダイニングバー(다이닝 바), バル(스페인식 선술집), 手羽先(닭 날개 요리)
  - 일식 일반: おでん(어묵 전골), 鳥料理(닭 요리 전문점)
    - 鳥料理는 타베로그상 焼き鳥와 한 묶음이지만, 이자카야 분위기가 전혀 없는 식사 위주 닭 요리집도 많아 예외 처리. 이자카야형 닭 요리집은 보통 주 장르가 焼き鳥나 居酒屋로 붙어 이자카야 그룹으로 분류됨
- 수집 제외 장르 (확정). 타베로그에서 맛집으로 찾을 대상이 아닌 장르
  - その他(기타) 대분류 전체: その他(기타), カラオケ(가라오케), ダーツ(다트 바), ホテル(호텔), 旅館・民宿(료칸·민박), 結婚式場(결혼식장), 道の駅(국도 휴게소), コンビニ・スーパー(편의점·슈퍼), 売店(매점)
  - 社員食堂(사원 식당), 学生食堂(학생 식당): 일반인 이용 불가
  - 料理旅館(요리 료칸), オーベルジュ(숙박형 레스토랑), 屋形船・クルージング(유람선 식사): 숙박·승선이 딸린 특수 형태
  - 가게에 붙은 장르가 **전부** 제외 목록에 있을 때만 제외. 호텔 안 레스토랑(フレンチ + ホテル)이나 가라오케 이자카야(居酒屋 + カラオケ)처럼 실제 식당 장르가 하나라도 있으면 유지

## 6. 사용자 안내 (앱 주의사항)

- 예약 가능으로 표시된 가게라도 인기 가게는 몇 달 전에 예약이 마감될 수 있으니 직접 확인해야 함 (확정)
- 가게 정보는 수집일 기준이라 가격·영업시간·휴폐업 여부가 바뀌었을 수 있음. 가게를 눌러 타베로그 페이지를 열면 최신 정보로 갱신됨
- (초안) "정보 없음"은 타베로그에 해당 정보가 없거나 아직 상세 페이지를 열어보지 않아 조건을 확인하지 못한 가게라는 뜻
